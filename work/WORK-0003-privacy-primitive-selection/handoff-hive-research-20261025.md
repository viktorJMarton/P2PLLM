## Recommendation for the cross-platform product

Keep the Rust node protocol, identity/session, privacy policy, task ledger and scheduler common across Android and Linux desktop. Build the first hive milestone as **capability discovery + authenticated sessions + resource reservations + task lifecycle** between two independently built nodes, with synthetic/public fixtures. Use request-level task routing as the first measured sharing baseline. For a private user request, remote execution remains unavailable until a local approved profile provides the actual protected operation and evidence. This follows the current [product contract](../../PRODUCT.md), [architecture](../../docs/architecture/overview.md), [threat model](../../docs/security/threat-model.md), [RFC-0002](../../docs/rfcs/RFC-0002-compute.md) and [empty registry](../../docs/security/privacy-profile-registry.md); it is a recommendation, not a new accepted decision.

Run the existing [WORK-0003 synthetic projection plan](experiment-plan.md) as a separate protected-computation experiment. If it passes, map a useful *bounded* Qwen subgraph under WORK-0005 and compare complete local versus protected distributed cost. A scalar or small matrix pass is a primitive milestone; it does not satisfy the cooperative AI or learning release gates. Learning is another workstream: pinned adapter format and aggregation, poisoning/output controls, optional differential privacy accounting, crash-safe local activation and rollback. Do not call aggregate hiding alone private learning.

### Primary evidence and what it does *not* prove

1. [libp2p AutoNAT](https://docs.libp2p.io/concepts/nat/autonat/), [relay and hole punching](https://docs.libp2p.io/concepts/hole-punching), [standalone connectivity](https://docs.libp2p.io/guides/standalone-connectivity/) support peer reachability discovery, relay reservations and direct-connection attempts. The [pub/sub documentation](https://docs.libp2p.io/concepts/pubsub/) says pub/sub itself does not discover peers. These are transport building blocks, not application authorization, physical-person identity, guaranteed connectivity, anonymity, or privacy of a computing peer's inputs. Pin actual rust-libp2p versions/features before implementation; measure Android NAT/carrier/Wi-Fi behavior instead of assuming always-on availability.
2. The original [Petals collaborative inference paper](https://arxiv.org/abs/2209.01188) and [later distributed inference/fine-tuning paper](https://arxiv.org/abs/2312.08361) motivate pipeline sharing over commodity Internet nodes. Their reported performance belongs to their model, peers, topology and workloads; it is not an A72 or Qwen measurement. Petals exposes hidden states, and [split-learning reconstruction/feature-hijack research](https://arxiv.org/abs/2012.02670) supplies a concrete adversarial reason to treat activations as sensitive. This is why no layer-split privacy claim follows from transport encryption.
3. [MP-SPDZ protocol matrix and benchmarking documentation](https://mp-spdz.readthedocs.io/en/latest/readme.html) distinguishes malicious/dishonest-majority MASCOT from semi-honest alternatives and warns that a runnable implementation is not by itself a production security review. [OpenFHE's security notes](https://openfhe-development.readthedocs.io/en/latest/sphinx_rsts/intro/security.html) describe IND-CPA/semi-honest assumptions and output-slot concerns. The existing WORK-0003 experiment plan already distinguishes public-W versus secret-W functionality, genuine preprocessing, designated output and Android/Linux feasibility. Neither source proves full private Qwen execution or useful mobile speed.
4. The original [federated averaging paper](https://research.google/pubs/communication-efficient-learning-of-deep-networks-from-decentralized-data/) supports local training plus update aggregation with reduced communication rounds in its study. The original [secure aggregation paper](https://research.google/pubs/practical-secure-aggregation-for-privacy-preserving-machine-learning/) supports aggregate hiding and dropout handling under its stated assumptions. [DiLoCo](https://arxiv.org/abs/2311.08105) proposes less frequent communication for distributed language-model training. These are separate techniques with different assumptions; none establishes secure, accurate, poison-resistant P2P Qwen adapter learning in this repository.
5. [Android background foreground-service restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start) and [background optimization](https://developer.android.com/topic/performance/background-optimization) constrain availability of phone peers. Model phone contribution as a revocable lease, bounded by user mode, battery/thermal/network policy and actual operating-system behavior. Desktop peers can be the initial stable anchor without becoming a plaintext data trustee.

## Heterogeneous-node experiment and decision sequence

1. Define signed, versioned capability advertisements as **untrusted claims**: device/backend/model+adapter revisions, operation/profile IDs, memory/threads, offered duration and resource limits. Validate locally and bind accepted values to a session/task; never accept a peer's `privacy_verified` claim. Use bootstrap/rendezvous or DHT discovery, but do not broadcast full private indexes. Test direct, relayed and failed NAT paths with an Android owner and an independently implemented Linux peer. Record connect success, RTT, relay byte rate, expiry and reconnect; sanitize identity/IP from shared evidence.
2. For public synthetic request-level routing, measure complete critical path: discovery if cold, authenticated session, reserve, queue, transfer, remote compute, result validation, retry/abort and release. Compare paired local execution on the same operation/model and measure phone CPU/memory/energy where instrumentation permits. No speedup, availability or quality claim without repeated device measurements.
3. For a pipeline/tensor lab, pin graph partition, exact model and tokenizer, activation sizes, bytes per generated token, sequential round trips, cache placement, numerical parity and dropout recovery. Measure LAN and WAN separately, and count relayed bytes. An attractive Petals benchmark cannot replace these target-device measurements. If activations are plaintext to a peer, label the mode synthetic/public only.
4. For protected arithmetic, retain the preregistered WORK-0003 public-W/secret-W distinction. Record setup/preprocessing, input preparation, online rounds, bytes, integrity checks, reconstruction/decryption, teardown and abort separately plus total p50/p95. Record both parties' CPU/RSS and actual target phone. A small primitive pass may guide WORK-0005 subgraph selection only after security review of exact parameters and output policy.
5. For learning, start with a frozen base-model revision, tokenizer, adapter schema/rank/target modules and normalized update semantics. Compare local-only, plain synthetic aggregation baseline and protected aggregation using the same corpus/metric. Report quality, update bytes, setup/round latency, dropouts, contributor-count/collusion assumptions, poisoning test and activation/rollback. No personal-derived updates enter the network before profile approval; any DP claim requires explicit unit, clipping, epsilon/delta/accountant and composition.

Decision order: measure local model quality and device feasibility under WORK-0002; implement interoperable public-fixture network/task lifecycle under WORK-0004; execute/review the bounded privacy experiment under WORK-0003; then choose a measured, useful protected subgraph for WORK-0005 and a separately reviewed adapter round for WORK-0006. The protocol should expose stable capability/status/error contracts now, while algorithms remain swappable only behind reviewed versioned profiles. The open privacy gate, Android availability, English/Hungarian quality and actual peer tests are blockers to product claims, not blockers to bounded research or transport implementation.

The [mathematical handoff](handoff-hive-math-20261025.md) and our reciprocal journal answers sharpen the measurement rule: report the **observed offer-to-verified-result wall time and critical path** even when component spans overlap; stratify connection/dropout by topology and Android state; do not turn a zero-failure binomial calculation into a service-availability claim. An adapter round must specify full-delta arithmetic or a protected reconstruction of factorized deltas, since averaging LoRA factors separately changes the model update. No Android model currently supplies a validated quality-matched comparator for a remote speedup claim. These are joint research recommendations, not accepted protocol or privacy-profile decisions.
